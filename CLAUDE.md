# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Everything runs from the repo root with the project venv (`.venv`, Python 3.14 or 3.12, both supported; `install/check.py` `PYTHON_SUPPORTED`). Packages are `-m` modules, not scripts.

Keep the code runnable on 3.12 while developing on 3.14: no 3.13+/3.14 syntax (unparenthesized `except A, B`, t-strings, type-parameter defaults) or stdlib modules (`annotationlib`, `compression.zstd`, ...) without an ImportError fallback, and `from __future__ import annotations` in any file whose annotations use a name defined later (3.12 evaluates them on import, 3.14 lazily). `tests/test_python_versions.py` checks all three.

```bash
.venv/bin/python -m pytest tests/ -q                                   # all tests
.venv/bin/python -m pytest tests/test_upload.py -q                     # one file
.venv/bin/python -m pytest tests/test_upload.py::test_add_gpa_uses_the_key_and_skips_pass_fail

.venv/bin/python -m upload                                             # <input-folder>/transcripts/*.pdf -> <work-folder>/transcripts
.venv/bin/python -m category_builder --category STEM [--builder llm] [--publish]
.venv/bin/python -m llm_category --category STEM --limit 3             # one builder directly
.venv/bin/python -m out_builder --category STEM [--builder llm]       # publish CSV to out-folder
.venv/bin/python -m category_definition_builder STEM --only chatgpt    # one definer step by hand, saves nothing
.venv/bin/python -m profile.profile_load                         # <work-folder>/personal/*.json -> in-memory dict
.venv/bin/python -m browser_view [--debug]                             # Flask UI on 127.0.0.1:5001
.venv/bin/python -m jev_category.seed --category STEM [--definition]   # local Jev scores -> the cloud's shared store
```

Tests need no Ollama, pdftotext, browser, or TypeSafe API. All of them are faked, and `tests/conftest.py` puts the repo root and `install/` on `sys.path`. There is no linter or build step.

Setting up a machine (venv, pdftotext, Ollama models, `config.yaml`) is done by the `/install-gpa-tools` skill (`.claude/skills/install-gpa-tools/`), which uses the scripts in `install/`. The venv alone, from a fresh clone, is the `/install-from-clone` skill: `install/setup_venv.py` picks the Python (`plan()`: 3.14, else 3.12, else uv; never installs uv or a Python itself) and installs `requirements.txt` + pytest.

## Architecture

The pipeline computes a per-student **category GPA** (STEM, MEDICAL, ...) from transcript PDFs:

```
PDF -> upload -> <work>/transcripts/<name>.common.json -> category builder -> <work>/<builder>/<cat>_gpa.csv + <cat>_courses.csv -> out_builder -> <out>/<cat>_gpa.csv
```

- **Folders** (`folders.py`): `components: [transcripts, letters, personal]`; each has `<input-folder>/<component>/` (raw input only: `.pdf`, `<key>_letter<N>.pdf`, `.json`; uploads are saved here, nothing a run makes) and `<work-folder>/<component>/` (only what is made from it: `.txt`/`.common.json`, letter `.txt`/`letter_ranks.csv`, profile `.json`). `folders.input_folder(cfg, c)` / `work_folder(cfg, c)` raise KeyError when the folder is unset (no default, so tests never touch real data) or `c` is not in `components`; `input_or_none`/`work_or_none` for pages that degrade. Builders stay at `<work-folder>/<builder>/`, browser profiles at `<work-folder>/browser-profiles/`. `letter_builder.letters_folder`/`letters_work_folder` and `profile_load.personal_folder`/`personal_work_folder`/`load_cfg` wrap them.
- **`config.yaml` is the single source of settings.** It holds the folders, the builder settings, the definer settings and `definitions-folder`, and it is tracked in git. Every package reads it. Category definitions are not in it: they are the local definitions repo (`category_builder/definitions.py`: `<definitions-folder>/<CAT>.json` = `{category, definition, origin: cloud|local, pending, updated_at}`, default `<work-folder>/definitions`). `Definitions(config_path).resolve(cat, draft)` = repo, else the cloud's shared one (copied in), else `draft()` offered to the cloud create-only (`publish`; the first client's text wins, a loser adopts the winner's; cloud down = local + pending, offered on next use); `update` = an edit (local override unless equal to the cloud's), `use_cloud` reverts. When the folder is missing, `init` makes it: moves an old `category-definitions:` section in and replaces it with `definitions-folder:` (the rest of config.yaml byte for byte; keep that guarantee if you touch config writing), then downloads every cloud definition. The cloud is `cloud_for(raw)`: jev `mode: cloud` with its token, else None (tests pass `cloud=`). The API key is never stored in it: `api-key-env` names the environment variable that holds it.
- **upload** turns `pdftotext -layout` output into the common transcript JSON. `upload/common/txt2common.py` parses with regexes plus `labels.json` and `template.json`, so every output has the template's keys. `add_gpa.py` then adds `gpa` (the school's own scale) and `gpa_4` (the common 0–4 scale from `standard_scale.json`) to each course. The GPA source is chosen in this order: optional `school_rules/<slug>.json`, then the transcript's grading key, then points/credits. Mismatches go into `warnings` and are never raised as errors. There is no OCR.
- **category_builder** is a registry and has no category logic of its own. `BUILDERS` in `category_builder/__init__.py` maps a name to a module that provides `load_config(config_path)` (which returns at least `folder`), `run(cfg, category, progress=None)` and an optional `estimate(...)`. Builders write their CSVs through `category_builder.common.write_outputs` and keep their caches in `<work>/<builder>/`. To add a builder, add one line to `BUILDERS` and a `category-builder: <name>:` section to config.yaml; the UI then lists it automatically. Builders only produce data: there is no ranking column, and no student is dropped.
  - `llm_category`: Ollama answers yes/no for each distinct course (code + title), at temperature 0 with schema-constrained output. The cache `cache_<cat>.json` is stamped with a hash of `category-build-model` plus the definition. Changing either one throws away all cached answers, which means hours of re-querying on CPU.
  - `jev_category`: the TypeSafe API scores each course 0–1, sent in batches, and a course counts as in the category when its score is above `threshold`. `builder.client(cfg)` picks the client by `mode`: `cloud` = `CloudClient` (the gpa-tools cloud server; the client token is `cloud-token-env` when set, else `~/.gpa-tools/client_token` (`GPA_TOOLS_HOME`; tests' autouse `gpa_tools_home` fixture points it at tmp): `jev_category/enroll.py` makes the laptop's own token at install, sends only its sha256 + email + hostname to `POST /v1/requests`, and on each start (`builder.cloud_token`, browser_view's start NOTICE) picks it up from `pending_token` once the owner approves it with `python -m jev_category.admin`; the token never leaves the laptop; server's model stamps the cache), `direct` = `JevClient` (TypeSafe with the key in `api-key-env`; dev only). Both offer `model`, `scores(category, definition, courses)` and `rank_letter(text)`; letter_builder uses the same client.
- **Client / cloud split.** The TypeSafe key must never be needed on a production client. `jev_core/` (`prompts.json` + Python `course_body`/`letter_body`/parse, tested against `fixtures.json`) is the shared question format, edited here; regenerate `fixtures.json` only when prompts.json changes on purpose. The server (JavaScript, Cloudflare Worker + R2; scores `scores/<model>/<CAT>/<sha256(definition)[:16]>.json` shared by all clients, definitions, tokens, token requests) is in the **private** repo `mini-cas-team/gpa-tools-cloud` (locally `../gpa-tools-cloud`), never in this public one: don't add server code or deploy secrets here. It keeps a copy of `jev_core/prompts.json` + `fixtures.json` (its `scripts/sync_jev_core.sh`), so after changing them here, sync and run its `npm test`. Owner tools here only call it: `python -m jev_category.admin` (token requests) and `jev_category.seed` (upload scores), both with the admin token in `GPA_TOOLS_CLOUD_ADMIN_TOKEN`.
- **Category definitions are shared by all builders.** When a category has no definition, `category_builder/definer.py` drafts one through `category_definition_builder`, which uses Playwright to drive the installed Chrome/Edge against the free ChatGPT and Gemini web chats with no account. The modes are `dev` (ChatGPT → Gemini → Ollama, in visible windows) and `prod` (headless Gemini → Ollama). `pipeline.py` runs each browser attempt in its own OS process with a hard deadline, because Playwright's sync API can't share a thread with Flask's request threads. `client.py` parses the reply's `DEFINITION: ... END` block. Site selectors live in `browser_legs.py` and break when the sites change; the chain then falls through to the next step.
- **browser_view** (`browser_view/app.py`, Flask with Jinja templates): the Upload tab runs upload, the definer and builds as background `CategoryJob`s, one at a time, and publishes the result after each build. The View tab reads `<work>/<builder>/<cat>_gpa.csv` and `_courses.csv` and serves the transcript PDFs. It is meant as a localhost tool for a single operator. Every View page (Transcripts, Recommendations, Profiles, Rank) uses the student dialog from `_student_dialog.html`: `studentRows(tbody, {builder, category})` highlights a clicked row and opens the dialog from an `a.student-link` (`data-file` = `<key>.pdf`).
- **profile**: `profile/display.py` flattens a profile for every page (each residence as three fields, `M.country`/`.state`/`.city` for `major_residence` and `S.*` for `second_residence`; `display.HINTS`/`hint(field)` is each field's meaning, the hover text of its column name on every page (Jinja globals `field_hint`, `profile_hints`); no `id_*`). `profile_load.load(folder)` reads every `*.json` in `<work-folder>/personal` into the module-level `PROFILES` dict, keyed by file name, and puts unreadable files in `ERRORS`. Upload → Profiles reads `<name>.json` files (uploaded and saved in `<input-folder>/personal`, else every one there) and saves each as `<work-folder>/personal/<name>.json` (adding `institution` and `program`, i.e. `student.major`, from the transcript with the same `student.name` when the profile lacks them; `profile/enrich.py` `FIELDS`), which is all that profile_load and the other pages read; View → Profiles reloads; the student dialog's Profile tab shows `<work-folder>/personal/<key>.json` (`_student_profile`). Upload → Summary (`/summary`, `_summary_rows`) is the union of transcript, letter and profile keys (`adam_flores`) with what each student has. The package name shadows the stdlib `profile`/`cProfile`.
- **summary**: View → Rank (`/view/rank`, headed Student Rank). `summary.ABS` subclasses each give one column through `rank() -> list[RankItem(name, order)]`; Rows are `summary.names.upload_names()`, the union of transcript, profile and letter names; `summary.table(objects, names)` gives each object's order per row name (exact match), None when it has none. Three objects so far: `summary.transcript.Transcript` (json `student.name`; three sub-columns via `columns()`, one per `SOURCES` column of the active builder's `<cat>_gpa.csv`: `category-gpa`, `all-courses-gpa`, `category-pct`; `rank()` and the page's first sort use `by`; `ranges={source: (low, high)}`: a value outside its source's inclusive range is None (`summary.filtered`), only in that sub-column, and no item is dropped; query params from `FILTERS`: `gpa_`, `all_gpa_`, `pct_` + `min`/`max`), `summary.recommendation.Recommendation` (title Recommend Letter, `letter_names`; two sub-columns via `columns()`: Score = group rank, Count = letter count; `rank()` gives the Score, the first sort when there is no Transcript column; `ranges` like Transcript's, query params from its `FILTERS`: `score_`, `count_` + `min`/`max`; no Rank by), and `summary.personal.Profile` (profile `name`; one sub-column per `show` field, default `DEFAULT_SHOW` institution and program; `rank()` gives the first; `profile_fields(cfg)` gives each field's `Field` kind: `RANGE_FIELDS` age, birth_date (ISO date), years_of_military_service filter by `ranges`, every other field is a string list filtered by `values` = {field: list[str]}, a value in the list (ignoring case) is shown, any other is None, an empty or None list keeps all; a filter blanks only its own field's values (`Profile._value`), never drops a profile; only a field in `show` filters, the others' filters are dropped (also by `_profile_query`, and turned off in the dialog); query params `prof_show`, `prof_min.<f>`/`prof_max.<f>`, `prof_in.<f>`, parsed by `_profile_query` and carried by `_profile_params`; no Rank by). The Config table has no Rank by column; the Transcript's is in its dialog only. An object may override `ABS.columns()` to give sub-columns (`Column.group` = its title; `summary.groups()` builds the two-row header as `Group`s; sortable `<th>`s carry `data-col`, which `_sort_table.html` uses). Each group also renders a hidden folded cell (`fold-col`, not sortable, its own body index after its sub-columns, heading `ABS.folded_title`) that the group header's ▲/▼ button swaps in for the `sub-col` cells, client-side, remembered in localStorage. Every name is a row (View → All); a filter blanks only its own sub-column's cells (the value is None), never another sub-column's or object's, and never drops a name; Valid = a value in every column. A column new or with different values since the tab last showed the page is orange (client-side, `student-rank-columns` in sessionStorage, class `changed`). Hover text explains each heading by its meaning: `ABS.description` (the group header, its folded cell and its Config button) and `ABS.hint(sub_title)` (each sub-column; `Column.hint`). A column whose orders are all numbers sorts as numbers (`Column.numeric`), else as text. A new column needs the class, a line in `_rank_objects` (app.py; shared by the page and Ask AI), and a Config row and dialog in `view_summary.html`; each dialog carries the other columns' query params as hidden inputs; for Ask AI also `filter_specs()`, `current_filters()` and `params()` (rank_ai below).
- **rank_ai**: Rank's Config → Ask AI (`POST /view/rank/ask?<the page's query>`, JSON `question`; returns `url` with the new filters, `explanation`, `unsupported`, `problems`, `source`; one request at a time; the page keeps the last 100 requests in localStorage, recalled with ↑/↓). The code never interprets the request: `prompt.build` = every `ABS.filter_specs()` (`summary.FilterSpec`: column, field, op `in`/`range`/`is`, meaning, known values, bounds; generated from the data) + `current_filters()` (`summary.Filter`) + the request verbatim + the answer format (one JSON object between BEGIN and END: `filters`, `explanation`, `unsupported`); the answer is the complete new filter list, not a delta. `answer.extract` takes the last JSON object with `filters` from any reply; `answer.check` keeps what fits the specs (values re-spelled as the data spells them) and lists the rest as problems, told back to the same provider up to `repairs` times. `providers.PROVIDERS` (ollama with `format=answer.SCHEMA`, gemini/chatgpt via `category_definition_builder.pipeline.ask`, claude via the Messages API with the key in `claude-api-key-env`) each has `ask(prompt) -> str`, tried in `rank-ai: providers` order; a failing one hands over. `params_for` gives each object its filters back through `ABS.params()`. Browser legs enter a multi-line prompt with Shift+Enter (`browser_legs.query`; one line is typed as before). Tests fake the providers with `monkeypatch.setitem(PROVIDERS, ...)`.
- Logs go to `<log-folder>/` as `upload.log`, `llm_category.log`, `jev_category.log`, `category_definer.log`, `rank_ai.log` and the browser_view log.

`README.md` documents the user-facing behavior in detail (config keys, UI flows, model sizing). Keep it in sync when behavior changes.
