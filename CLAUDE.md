# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Everything runs from the repo root with the project venv (`.venv`, Python 3.14 or 3.12, both supported; `install/check.py` `PYTHON_SUPPORTED`). Packages are `-m` modules, not scripts.

Keep the code runnable on 3.12 while developing on 3.14: no 3.13+/3.14 syntax (unparenthesized `except A, B`, t-strings, type-parameter defaults) or stdlib modules (`annotationlib`, `compression.zstd`, ...) without an ImportError fallback, and `from __future__ import annotations` in any file whose annotations use a name defined later (3.12 evaluates them on import, 3.14 lazily). `tests/test_python_versions.py` checks all three.

```bash
.venv/bin/python -m pytest tests/ -q                                   # all tests
.venv/bin/python -m pytest tests/test_upload.py -q                     # one file
.venv/bin/python -m pytest tests/test_upload.py::test_add_gpa_uses_the_key_and_skips_pass_fail

.venv/bin/python -m upload                                             # <input-folder>/transcripts/*.pdf -> <work-folder>/transcripts
.venv/bin/python -m category_builder --category STEM [--builder llm] [--publish]
.venv/bin/python -m llm_category --category STEM --limit 3             # one builder directly
.venv/bin/python -m out_builder --category STEM [--builder llm]       # publish CSV to out-folder
.venv/bin/python -m category_definition_builder STEM --only chatgpt    # one definer step by hand, saves nothing
.venv/bin/python -m profile.profile_load                         # <work-folder>/personal/*.json -> in-memory dict
.venv/bin/python -m browser_view [--debug]                             # Flask UI on 127.0.0.1:5001
```

Tests need no Ollama, pdftotext, browser, or TypeSafe API. All of them are faked, and `tests/conftest.py` puts the repo root and `install/` on `sys.path`. There is no linter or build step.

Setting up a machine (venv, pdftotext, Ollama models, `config.yaml`) is done by the `/install-gpa-tools` skill (`.claude/skills/install-gpa-tools/`), which uses the scripts in `install/`. The venv alone, from a fresh clone, is the `/install-from-clone` skill: `install/setup_venv.py` picks the Python (`plan()`: 3.14, else 3.12, else uv; never installs uv or a Python itself) and installs `requirements.txt` + pytest.

## Architecture

The pipeline computes a per-student **category GPA** (STEM, MEDICAL, ...) from transcript PDFs:

```
PDF -> upload -> <work>/transcripts/<name>.common.json -> category builder -> <work>/<builder>/<cat>_gpa.csv + <cat>_courses.csv -> out_builder -> <out>/<cat>_gpa.csv
```

- **Folders** (`folders.py`): `components: [transcripts, letters, personal]`; each has `<input-folder>/<component>/` (raw input only: `.pdf`, `<key>_letter<N>.pdf`, `.profile`; uploads are saved here, nothing a run makes) and `<work-folder>/<component>/` (only what is made from it: `.txt`/`.common.json`, letter `.txt`/`letter_ranks.csv`, profile `.json`). `folders.input_folder(cfg, c)` / `work_folder(cfg, c)` raise KeyError when the folder is unset (no default, so tests never touch real data) or `c` is not in `components`; `input_or_none`/`work_or_none` for pages that degrade. Builders stay at `<work-folder>/<builder>/`, browser profiles at `<work-folder>/browser-profiles/`. `letter_builder.letters_folder`/`letters_work_folder` and `profile_load.personal_folder`/`personal_work_folder`/`load_cfg` wrap them.
- **`config.yaml` is the single source of settings.** It holds the folders, the builder settings, the definer settings and the category definitions, and it is tracked in git. Every package reads it, and `browser_view` writes to it. `category_builder/definitions.py` rewrites only the `category-definitions:` section and leaves the rest of the file, comments included, byte for byte. Keep that guarantee if you touch config writing. The API key is never stored in it: `api-key-env` names the environment variable that holds it.
- **upload** turns `pdftotext -layout` output into the common transcript JSON. `upload/common/txt2common.py` parses with regexes plus `labels.json` and `template.json`, so every output has the template's keys. `add_gpa.py` then adds `gpa` (the school's own scale) and `gpa_4` (the common 0–4 scale from `standard_scale.json`) to each course. The GPA source is chosen in this order: optional `school_rules/<slug>.json`, then the transcript's grading key, then points/credits. Mismatches go into `warnings` and are never raised as errors. There is no OCR.
- **category_builder** is a registry and has no category logic of its own. `BUILDERS` in `category_builder/__init__.py` maps a name to a module that provides `load_config(config_path)` (which returns at least `folder`), `run(cfg, category, progress=None)` and an optional `estimate(...)`. Builders write their CSVs through `category_builder.common.write_outputs` and keep their caches in `<work>/<builder>/`. To add a builder, add one line to `BUILDERS` and a `category-builder: <name>:` section to config.yaml; the UI then lists it automatically. Builders only produce data: there is no ranking column, and no student is dropped.
  - `llm_category`: Ollama answers yes/no for each distinct course (code + title), at temperature 0 with schema-constrained output. The cache `cache_<cat>.json` is stamped with a hash of `category-build-model` plus the definition. Changing either one throws away all cached answers, which means hours of re-querying on CPU.
  - `jev_category`: the TypeSafe API scores each course 0–1, sent in batches, and a course counts as in the category when its score is above `threshold`.
- **Category definitions are shared by all builders.** When a category has no definition, `category_builder/definer.py` drafts one through `category_definition_builder`, which uses Playwright to drive the installed Chrome/Edge against the free ChatGPT and Gemini web chats with no account. The modes are `dev` (ChatGPT → Gemini → Ollama, in visible windows) and `prod` (headless Gemini → Ollama). `pipeline.py` runs each browser attempt in its own OS process with a hard deadline, because Playwright's sync API can't share a thread with Flask's request threads. `client.py` parses the reply's `DEFINITION: ... END` block. Site selectors live in `browser_legs.py` and break when the sites change; the chain then falls through to the next step.
- **browser_view** (`browser_view/app.py`, Flask with Jinja templates): the Upload tab runs upload, the definer and builds as background `CategoryJob`s, one at a time, and publishes the result after each build. The View tab reads `<work>/<builder>/<cat>_gpa.csv` and `_courses.csv` and serves the transcript PDFs. It is meant as a localhost tool for a single operator. Every View page (Transcripts, Recommendations, Profiles, Rank) uses the student dialog from `_student_dialog.html`: `studentRows(tbody, {builder, category})` highlights a clicked row and opens the dialog from an `a.student-link` (`data-file` = `<key>.pdf`).
- **profile**: `profile/display.py` flattens a profile for every page (each residence as three fields, `M.country`/`.state`/`.city` for `major_residence` and `S.*` for `second_residence`; `display.HINTS`/`hint(field)` is each field's meaning, the hover text of its column name on every page (Jinja globals `field_hint`, `profile_hints`); no `id_*`). `profile_load.load(folder)` reads every `*.json` in `<work-folder>/personal` into the module-level `PROFILES` dict, keyed by file name, and puts unreadable files in `ERRORS`. Upload → Profiles reads `<name>.profile` files (uploaded and saved in `<input-folder>/personal`, else every one there) and saves each as `<work-folder>/personal/<name>.json` (adding `institution` and `program`, i.e. `student.major`, from the transcript with the same `student.name` when the profile lacks them; `profile/enrich.py` `FIELDS`), which is all that profile_load and the other pages read; View → Profiles reloads; the student dialog's Profile tab shows `<work-folder>/personal/<key>.json` (`_student_profile`). Upload → Summary (`/summary`, `_summary_rows`) is the union of transcript, letter and profile keys (`adam_flores`) with what each student has. The package name shadows the stdlib `profile`/`cProfile`.
- **summary**: View → Rank (`/view/summary`, headed Student Rank). `summary.ABS` subclasses each give one column through `rank() -> list[RankItem(name, order)]`; Rows are `summary.names.upload_names()`, the union of transcript, profile and letter names; `summary.table(objects, names)` gives each object's order per row name (exact match), None when it has none. Three objects so far: `summary.transcript.Transcript` (json `student.name`; three sub-columns via `columns()`, one per `SOURCES` column of the active builder's `<cat>_gpa.csv`: `category-gpa`, `all-courses-gpa`, `category-pct`; `rank()` and the page's first sort use `by`; `ranges={source: (low, high)}`: a value outside its source's inclusive range is None (`summary.filtered`), only in that sub-column, and no item is dropped; query params from `FILTERS`: `gpa_`, `all_gpa_`, `pct_` + `min`/`max`), `summary.recommendation.Recommendation` (title Recommend Letter, `letter_names`; two sub-columns via `columns()`: Score = group rank, Count = letter count; `rank()` gives the Score, the first sort when there is no Transcript column; `ranges` like Transcript's, query params from its `FILTERS`: `score_`, `count_` + `min`/`max`; no Rank by), and `summary.personal.Profile` (profile `name`; one sub-column per `show` field, default `DEFAULT_SHOW` institution and program; `rank()` gives the first; `profile_fields(cfg)` gives each field's `Field` kind: `RANGE_FIELDS` age, birth_date (ISO date), years_of_military_service filter by `ranges`, every other field is a string list filtered by `values` = {field: list[str]}, a value in the list (ignoring case) is shown, any other is None, an empty or None list keeps all; a filter blanks only its own field's values (`Profile._value`), never drops a profile; only a field in `show` filters, the others' filters are dropped (also by `_profile_query`, and turned off in the dialog); query params `prof_show`, `prof_min.<f>`/`prof_max.<f>`, `prof_in.<f>`, parsed by `_profile_query` and carried by `_profile_params`; no Rank by). The Config table has no Rank by column; the Transcript's is in its dialog only. An object may override `ABS.columns()` to give sub-columns (`Column.group` = its title; `summary.groups()` builds the two-row header as `Group`s; sortable `<th>`s carry `data-col`, which `_sort_table.html` uses). Each group also renders a hidden folded cell (`fold-col`, not sortable, its own body index after its sub-columns, heading `ABS.folded_title`) that the group header's ▲/▼ button swaps in for the `sub-col` cells, client-side, remembered in localStorage. Every name is a row (View → All); a filter blanks only its own sub-column's cells (the value is None), never another sub-column's or object's, and never drops a name; Valid = a value in every column. Hover text explains each heading by its meaning: `ABS.description` (the group header, its folded cell and its Config button) and `ABS.hint(sub_title)` (each sub-column; `Column.hint`). A column whose orders are all numbers sorts as numbers (`Column.numeric`), else as text. A new column needs the class, a line in the route's object list, and a Config row and dialog in `view_summary.html`; each dialog carries the other columns' query params as hidden inputs.
- Logs go to `<log-folder>/` as `upload.log`, `llm_category.log`, `jev_category.log`, `category_definer.log` and the browser_view log.

`README.md` documents the user-facing behavior in detail (config keys, UI flows, model sizing). Keep it in sync when behavior changes.
